## Context

現在のタスク追加・編集ダイアログは `<input type="time" step="1800">` を使っており、ブラウザ標準の時刻ピッカーは時・分が別々の操作対象（セグメント）になっている。にもかかわらず時・分を別々に操作させるのは過剰な手間であり、単一の選択操作（プルダウン）に置き換える。

タイムラインの表示グリッド（30分刻みの行、`SLOT_MINUTES`）と、タスクの開始・終了時刻として選択できる粒度は別の関心事として扱う。表示グリッドは既存どおり30分刻みを維持し、プルダウンで選べる時刻の粒度は15分刻みに広げる（30分単位の行の中に15分単位でタスクの開始・終了を置けるようにする）。

Constraints:
- タイムライン表示グリッドの粒度（`SLOT_MINUTES` = 30分、`SLOTS_PER_DAY`）は変更しない。
- タスクの開始・終了時刻として選択・保存できる粒度は07:30〜18:00の範囲内で15分刻みとする。
- 保存・バリデーション・タイムライン描画など既存のデータフロー（`{ name, startTime, endTime }`のHH:MM文字列を受け取る）の形は変更しない。

## Goals / Non-Goals

**Goals:**
- 開始・終了時刻の入力を、時・分を1回の選択で確定できる単一プルダウンに置き換える。
- 選択肢そのものを07:30〜18:00・15分刻みに限定し、範囲外や中途半端な時刻を選べないようにする。
- 終了時刻の選択肢を開始時刻に応じて動的に絞り込み、開始時刻より後の値のみを選べるようにする。
- 時刻範囲・選択粒度の定義を`timeSlots.js`に一本化し、UIとロジックの間で値がずれないようにする。
- タイムラインの表示グリッド（30分刻みの行）は変更せず、15分刻みで選ばれた開始・終了時刻もその上に正しい位置・高さで描画されるようにする。

**Non-Goals:**
- 07:30〜18:00という範囲自体の変更。
- タイムライン表示グリッドの行の粒度（30分刻み）の変更。
- タスクデータモデルやバリデーションルール（`startTime < endTime`など）の変更。
- カスタムデザインのドロップダウンコンポーネント導入（ネイティブ`<select>`を使う）。

## Decisions

1. 時刻選択肢の生成をユーティリティ関数として`timeSlots.js`に追加し、選択粒度は15分とする
- Decision: `DAY_START_TIME`〜`DAY_END_TIME`を15分刻みで列挙した「HH:MM」文字列配列を返す関数（`listDayTimes()`）を追加する。タイムライン描画用の`SLOT_MINUTES`（30分）とは独立した定数（例: `TIME_OPTION_MINUTES` = 15）として定義する。
- Rationale: 時刻範囲・選択粒度の情報源を1箇所に保ち、UI側での重複定義や将来のズレを防ぐ。表示グリッドの粒度とタスク時刻の選択粒度は異なる関心事のため、別定数として分離する。
- Alternative considered: HTML側に`<option>`を静的に列挙する案。範囲や刻みを変更した際にHTMLとJSの両方を修正する必要があり、ズレのリスクが高いため不採用。
- Alternative considered: 選択粒度もタイムライン表示グリッドと同じ30分刻みのままにする案。今回のユーザー要望（15分刻みでの選択）に応えられないため不採用。

2. `<input type="time">`を`<select>`に置き換え、選択肢は起動時にJSで生成する
- Decision: `index.html`の`#start-time`・`#end-time`を`<select>`要素にし、`main.js`がダイアログを開くタイミングで選択肢を挿入する。
- Rationale: 選択肢の生成元を`timeSlots.js`の1関数に統一でき、HTMLを静的に保守する必要がなくなる。
- Alternative considered: HTML側に固定の`<option>`一覧を書く案。決定1と同じ理由で不採用。

3. 終了時刻の選択肢は開始時刻の変更に連動して再生成する
- Decision: 開始時刻`<select>`の`change`イベントで、終了時刻`<select>`の選択肢を「開始時刻より後の時刻のみ」に絞り込んで再構築する。既に選択されていた終了時刻が絞り込み後も有効なら維持し、無効になった場合は先頭の有効な選択肢（開始時刻の15分後）を既定値にする。
- Rationale: 無効な組み合わせをそもそも選べなくすることで、「入力が面倒」という課題の根本（時・分を別々に、かつ正しい組み合わせで選ぶ手間）を解消する。
- Alternative considered: 終了時刻の選択肢を常に全時刻にし、送信時のバリデーションのみで弾く案。無効な組み合わせを一旦選べてしまい、体験改善の効果が薄いため不採用。

4. 既存の`normalizeTaskInput`によるサーバー側（状態管理側）バリデーションは維持し、許容粒度を15分に広げる
- Decision: UIが不正な組み合わせを選べなくする一方で、`taskStore`の`normalizeTaskInput`による`startTime < endTime`・範囲チェックはそのまま残す。時刻フォーマットの検証（`isTimeFormat`相当）は30分刻みから15分刻み（分が00/15/30/45）の許容に変更する。
- Rationale: UIとロジックの二重防御を保ち、将来UIを介さない呼び出し（テストや別UIなど）があっても不正データを防げる。UIの選択粒度と検証粒度を一致させないと、UIから送られた正当な15分刻みの値がロジック側で誤って拒否されてしまう。
- Alternative considered: UI側で担保できるためロジック側の検証を簡略化する案。防御の層を減らすメリットがなく、テストとの整合性も崩れるため不採用。

5. `<select>`の見た目は既存の入力欄デザイントークンに合わせる
- Decision: `app.css`内で`<select>`にも既存の`#task-form input`と同等のボーダー・角丸・パディング・フォントを適用する。
- Rationale: フォーム内の見た目の一貫性を保ち、寒色系テーマの統一感を崩さない。
- Alternative considered: 独自スタイルのカスタムドロップダウンを実装する案。依存ライブラリなしの現状の実装方針から外れ、アクセシビリティ対応コストも増えるため不採用。

6. 15分刻みで選ばれた時刻は、30分刻みのタイムライン表示グリッド上に分数値の位置として描画する
- Decision: タスクの`startSlot`/`endSlot`は「30分を1単位とした相対値」のまま据え置き、15分刻みの時刻を変換すると小数値（例: 08:15 → 1.5）になることを許容する。タイムライン描画は既に`top`/`height`を`(slot / SLOTS_PER_DAY) * 100%`というパーセンテージ計算で行っており、小数値でもそのまま正しい位置・高さになる。行の描画（`createSlotRow`によるグリッド線・時刻ラベル）は整数の`slot`（0〜`SLOTS_PER_DAY`）のみを使い続けるため、30分刻みの見た目は変わらない。
- Rationale: 表示グリッドの粒度（30分）と選択粒度（15分）を分離しつつ、既存のパーセンテージベースの描画ロジックを変更せずに両立できる。
- Alternative considered: タイムライン表示グリッド自体を15分刻み（`SLOT_MINUTES` = 15）に変更する案。行数が倍増し見た目が過密になるうえ、今回のユーザー要望は「選択のしやすさ」であり表示グリッドの変更は求められていないため不採用。

## Risks / Trade-offs

- [ブラウザ・OSごとにネイティブ`<select>`の見た目が微妙に異なる] -> Mitigation: 既存の入力欄と同じCSSトークン（ボーダー色・角丸・パディング）を適用し、大きな差異が出ないようにする。既にダイアログやボタンでもネイティブ要素を使っており許容範囲。
- [開始時刻変更時に終了時刻の選択肢を再生成すると、選択済みの終了時刻がリセットされる場合がある] -> Mitigation: 再生成時に「現在の終了時刻が新しい開始時刻より後であればそのまま維持する」ロジックを入れ、不要なリセットを避ける。
- [選択肢生成処理をダイアログを開くたびに実行するコスト] -> Mitigation: 選択肢は最大43件程度であり、ダイアログを開いた時・開始時刻変更時のみ実行するため無視できるコスト。
- [表示グリッド（30分）と選択粒度（15分）が異なることで、タスクブロックがグリッド線の中間から始まる見た目になる] -> Mitigation: これは意図した挙動（Outlookなどでも30分グリッド上に任意時刻のイベントを描画できる）であり、パーセンテージベースの描画で自然に表現される。

## Migration Plan

- データモデル（`{ id, name, startTime, endTime, startSlot, endSlot }`）に変更はないため、データ移行は不要。
- 展開手順: 本変更をブランチ上で実装し、`npm test`でユニットテストを通し、`npm run build`で`dist/index.html`を再生成し、手動QA（追加・編集・削除・時刻選択の絞り込み）を行った上で反映する。
- ロールバック: UI入力コントロールの変更のみで永続データへの影響がないため、関連コミットの巻き戻しで対応可能。

## Open Questions

- なし（将来07:30〜18:00の範囲自体を変更する場合も、`timeSlots.js`の定数と選択肢生成関数を変更するだけで済む設計としている）。
