## Context

この変更では、Outlook風の1日表示レイアウトを持つ専用デイリー・スケジューラを導入します。現時点のリポジトリには実装モジュールがないため、本設計では実装前に基準となるアーキテクチャとUX挙動を定義します。

Constraints:
- 計画対象は1日のみとする。
- 時間粒度は30分スロットに固定する。
- タスクデータモデルはタスク名、開始時刻、終了時刻のみを含む。
- 画面は寒色系を基調とし、長時間見ても負担が少ないこと。

Stakeholders:
- 1日の予定を素早く計画・調整したいエンドユーザー。
- 予測可能なUI状態管理とバリデーション挙動を必要とする将来の保守担当者。

## Goals / Non-Goals

**Goals:**
- 1日分を明確に表示できるOutlook風デイビュー・タイムラインを提供する。
- タスクの追加・編集・削除を行うと即時に表示へ反映されること。
- 正しいタスク時間範囲（start < end、30分単位、同日内）を強制すること。
- 寒色系パレットで、落ち着き・可読性・目のやさしさを両立すること。
- データ層とUI層を独立して進化させられるよう、実装をモジュール化すること。

**Non-Goals:**
- 複数日表示、週表示、月表示などのカレンダー拡張。
- 繰り返しタスク、リマインダー、通知、外部同期連携。
- 名前・開始時刻・終了時刻以外のリッチなタスク属性。

## Decisions

1. Componentized architecture (timeline grid + task editor + state store)
- Decision: タイムライン描画、タスク入力フォーム/ダイアログ、状態管理を分離したモジュール構成にする。
- Rationale: 結合度を下げ、後続機能追加を容易にする。
- Alternative considered: 1つの巨大ページコンポーネントに集約する案。CRUDと検証ロジックのテスト性・保守性が下がるため不採用。

2. Normalized in-memory task model with deterministic sorting
- Decision: 各タスクを `{ id, name, startTime, endTime }` で保持し、`startTime`→`endTime` の順で安定ソートする。
- Rationale: 表示順のぶれを防ぎ、重なり判定を単純化できる。
- Alternative considered: 表示順のみを状態として保持する案。検証や編集時に不整合が起きやすいため不採用。

3. Slot-based time calculations
- Decision: 時刻を30分スロットのインデックス（0-47）へ変換し、レイアウト計算と重なり判定に使用する。
- Rationale: 30分単位の必須要件に合致し、時刻由来のレイアウト誤差を避けやすい。
- Alternative considered: 生のタイムスタンプから直接ピクセル位置を算出する案。精度面と保守性の懸念から不採用。

4. Inline validation at input and submit
- Decision: 入力変更時と送信時の両方で、必須入力と時間制約を検証する。
- Rationale: ユーザーに即時フィードバックを返し、不正データの保存を防げる。
- Alternative considered: 送信時のみ検証する案。エラー発見が遅れるため不採用。

5. Theme tokens for cool, eye-friendly visuals
- Decision: 背景/サーフェス/境界線/主要色/アクセント/文字色の意味論的トークンを定義し、寒色系かつ十分なコントラストを確保する。
- Rationale: 再利用可能なトークンで一貫性とアクセシビリティを担保しやすい。
- Alternative considered: コンポーネントごとの場当たり的な配色。UX不統一と保守負荷増大のため不採用。

## Risks / Trade-offs

- [Outlook風という期待とのギャップ] -> Mitigation: まずは日付列・時間行など馴染みある構造を優先し、未対応機能を明示する。
- [同時刻タスクの重なり描画の複雑化] -> Mitigation: 横並びレーン方式で開始し、レーン割当の決定性テストを追加する。
- [30分固定制約が窮屈に感じられる可能性] -> Mitigation: 丸め・制約ルールをUI上で明確に案内する。
- [色の感じ方に個人差がある] -> Mitigation: 彩度を抑え、WCAGを意識したコントラスト確認を行う。

## Migration Plan

- 初回実装ではデータ移行は不要。
- 展開計画: 通常ルート配下で機能実装し、手動QAとユニットテストで検証後に標準スケジューラ画面として昇格する。
- ロールバック: 永続データ変換を伴わないため、関連コミットの巻き戻しで対応可能。
